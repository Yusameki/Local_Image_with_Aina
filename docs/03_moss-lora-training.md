# LoRA 炼丹实录：从 Synthetic Data 到 180 张矩阵盲选

> 这是在 12 GB 显存上，用 70 张自家 SDXL 出图，给 MOSS-Image 训一支画风 LoRA 的完整记录。
> 最终结论：**300 步是泛化能力的甜点区**，18 组盲选里它拿了 14 票。

---

## 1. 为什么用「自己出的图」当训练集

一开始的想法很自然：去找原画师的作品来训。后来放弃了，理由有三条：

| 理由 | 说明 |
|---|---|
| **口径一致** | 我们想要的是「我们已经调好的那个画风」，不是「画师的原始画风」。自己出的图天然就是这个口径。 |
| **可控** | 构图、光比、服装全是自己定的，不会混进一堆不想要的元素。 |
| **干净** | 不存在版权与来源问题，随便训、随便发。 |

所以最终数据集是 **70 张 `768 × 1664` 的 SDXL 出图**，就是 `01_sdxl-workflow.md` 那套配方产出的。

> 一个反直觉的经验：**AI 出图的瑕疵会被当成「画风」学走**。
> 手部畸形、结构错位、糊成一团的衣褶——模型不知道那是错误，它只知道「这张图长这样」。
> 所以挑图时唯一必须剔除的是**真正的结构崩坏**，其余（发色不同、服装不同）都是优点不是缺点。

## 2. 打标：写什么，就等于告诉模型「什么是内容」

这是整个训练里最重要的一条认知：

> **caption 里写了什么，模型就认为那是「内容」；没写的，才会归给「风格」。**

既然目标是**画风 LoRA**，那所有跟风格有关的词都要删干净：

```
❌ [媒介词], [笔触描述], [画师名], [质量词], [艺术形式]
✅ [主体], [人数], [景别], [场景要素…]
```

前者会把「水彩感」降级成一种「内容标签」；后者才能让模型把笔触归到权重里。

**实际用的模板**（由文件名里的场景词批量生成）：

```
[主体], [人数], [景别], [场景词]
```

再加一层小技巧：**把数据集目录命名成 `1_[触发词]` 的形式**。
KohakuMossTrainer（以及 sd-scripts 系）会把目录名里 `_` 之后的部分自动当作
**触发词**注入到每一条 caption，不用手写。

最终每张图的 caption 就是：`[触发词]` + 上面那串内容描述。

## 3. 数据体检

训练前先跑一遍 `inspect_data.py`，看两个数：

| 指标 | 实测 | 判断 |
|---|---|---|
| 尺寸分桶 | 1488×688 ×68 / 1216×832 ×2 | 基本统一，可接受 |
| `crop_loss` | 0.17% | 很小，说明裁切几乎没切掉主体 |
| tokens/step | ≈ 4000 | 对应 `vram_12g` 档的 6144 上限，有余量 |

> `crop_loss` 是你真正该看的数字。它代表「为了凑成训练分辨率，有多少像素被切掉了」。
> 这个数一大，等于在教模型「人物的头是可以被切掉的」。

## 4. 硬件现实：sm86 没有 fp8

很多人以为「省显存 = 开 fp8」。在 RTX 3080 Ti 上这条路是断的：

| 架构 | 精度路径 |
|---|---|
| sm80 / **sm86**（30 系） | bf16 / fp16，**无 fp8 compute** |
| sm89（40 系） | 有 fp8 / MXFP8 |
| sm90 / sm100 | 支持 |

所以 3080 Ti 拿到的是 **bf16 + Triton kernel** 这条路。
不是「没开 fp8」，是**硬件层面就没有**。

Windows 上 sm75 / sm86 / sm89 / sm120 的单卡功能是全支持的，
多卡训练（DDP/FSDP）才需要 Linux。

## 5. 配置：`vram_12g` 档位到底做了什么

KohakuMossTrainer 内置了几档预设，12 GB 对应的是：

```
vram_12g:
  4 resident blocks（DiT 42 层里只常驻 4 层）
  activation + gradient offload
  optimizer states 放主机内存
  6144 tokens/step
  text encoder 流式加载（用完即弃）
  VAE offloaded
```

对照一下其他档位，就能看出它省在哪：

| 档位 | 常驻 block | tokens/step | 备注 |
|---|---|---|---|
| `vram_24g` | 16 | 12288 | balanced |
| `vram_16g` | 4 | 8192 | |
| **`vram_12g`** | **4** | **6144** | act+grad offload，host optimizer |
| `vram_8g` | 2 | 4352 | minimal，主机内存约 19 GiB |
| `vram_6g` | 2 | — | 需要两个离线缓存，很折腾 |

**LoRA 训练不需要动全参微调的预算。** 全参在 12 GB 卡上是不现实的
（单卡全参步内约 70 GiB 主机内存），但 LoRA adapter 的显存占用跟这个完全不是一个量级——
实测峰值只有 **4.7 GiB**。

启动命令（含两处必踩的坑，见下节）：

```bash
kogine run scripts/train/moss.py \
  --config configs/user/mylora.py \
  --set LR=2e-4 \
  --set STEPS=1000 \
  --set SAVE_EVERY=100 \
  --set KEEP_LAST=0 \
  --set 'SCHEDULE={"mode":"cosine","warmup":10,"end":-1,"min_value":0.1}'
```

## 6. 两个吃时间的坑

### 6.1 `warmup >= STEPS` 直接拒跑

默认配置 `warmup=100`。如果你只想先跑 100 步验证一下：

```
invalid configuration: SCHEDULE warmup=100 >= its end 100 (STEPS):
the schedule never leaves warmup
```

修法是把整个 schedule 覆盖掉（注意引号，要让 shell 把 JSON 当成一个参数）：

```bash
--set 'SCHEDULE={"mode":"cosine","warmup":10,"end":-1,"min_value":0.1}'
```

### 6.2 `KEEP_LAST` 默认是 3，会把你中间的 checkpoint 吃掉

这一条坑掉了我们半小时。

跑 1000 步、`SAVE_EVERY=100`，本以为会留下 10 个 checkpoint，
结果 **`KEEP_LAST` 默认值 3**，中间的全被删了，只剩 800 / 900 / 1000。

**必须显式写 `--set KEEP_LAST=0`。**

> 而且这件事还有个更隐蔽的后果：
> 如果你后来想「补跑一下 600、700 步」，**千万不要分段跑**。
> 分段训练会让不同 step 落在不同的学习率曲线上，横比就不公平了。
> 正确做法是**从头重跑一次完整 1000 步**，一晚上 58 分钟的事。

## 7. 训练实测数据

| 项 | 值 |
|---|---|
| 数据 | 70 张 768×1664 |
| 步数 | 1000 |
| 单步耗时 | **3.4 s** |
| 总时长 | **58 分钟** |
| 末步 loss | 0.2807 |
| 显存峰值 | **4.7 GiB** |
| 产出 | 10 个 checkpoint（step_100 … step_1000） |

> 前 100 步跑完约 5 分钟，其中 **153 秒是一次性的 kernel 预热**（Triton 编译）。
> 所以「先跑 100 步看看」的成本比想象的低。

导出成 ComfyUI 单文件格式：

```bash
kogine run scripts/export.py --config configs/user/mylora.py --format comfy
# → runs/moss/mylora/export/mylora-comfy.safetensors（约 142 MB）
```

放到 `models/loras/` 就能用普通 `LoraLoader` 加载了。
注意 **`strength_clip` 要给 0**——我们只训了 DiT 侧，clip 侧没有任何变化。

## 8. 180 张矩阵：把「哪档最好」变成可复现的实验

十个 checkpoint 训完，问题来了：**到底哪一档最好？**

凭记忆抽卡是不靠谱的。所以做了一个穷举矩阵：

```
10 个 checkpoint × 3 档强度 (0.6 / 0.8 / 1.0) × 2 个场景 (亮 / 暗) × 3 个种子 = 180 张
```

**关键的实验设计**：

- **种子全表统一**（4401 / 4402 / 4403）。这样同一个种子下的差异，只能来自 checkpoint 与强度，
  不会被「这张运气好」污染。
- **两个场景故意做成极端**：海边白裙（高亮、大面积白）对「过曝」最敏感；
  赛博暗室（几乎全黑）对「人物没入黑暗」最敏感。两个都过，才算过关。
- 参数固定：832×1808 / 50 步 / CFG 3 / euler / sgm_uniform。

脚本见 `scripts/moss-matrix-batch.py`。实测跑完 **180/180 成功，0 失败，159 分钟**，
单张 48–60 秒，显存峰值 11140 MiB。

### 8.1 排版方式

一开始拼成「10 行 × 9 列」的大表，太挤，根本看不出差别。
后来改成**「18 组横向长廊」**：每个「场景 × 强度 × 种子」组合一条长图，
从左到右排 100…1000 十张，每张上方标步数。

这样一眼就能看出**随步数变化的趋势**——这才是这张图真正想表达的东西。

### 8.2 Excel 盲选

18 条长图看下来，人会疲劳。所以做了一张表，每组填「最好的步数 / 最差的步数」，
F/G 列用数据验证下拉（只能选 100…1000），另开一个 sheet 用 `COUNTIFS`
按亮/暗场景统计每个步数被选中的次数。

> **为什么要用表格而不是直接看着图说结论？**
> 因为看图的时候你记得住「这张好好看」，记不住「这是第几张、什么参数」。
> 18 组看完，记忆已经混了。表格是把判断**落成数据**，统计才有意义。

## 9. 结果：300 步拿走 14/18

| 场景 | 最好 | 最差 |
|---|---|---|
| 亮（海边白裙） | 300 ×6、1000 ×2、700 ×1 | 100 ×2、200 ×4、500 ×1 |
| 暗（赛博暗室） | 300 ×8、800 ×1 | 100 ×1、200 ×1、500 ×2、600 ×2、800 ×? |

**300 步合计 14/18**，压倒性胜出。

评语摘录：

- 300 步：「神仙」「封神」「无敌」，肤色和结构的平衡最好；
- 200 步：氛围最好，但**容易崩**（结构不稳）；
- 600 步：「崩完了」；
- 900 / 1000 步：亮场景**头身比走形**。

最终配方：**300 步 checkpoint，亮场景用 0.8，暗场景用 1.0。**

## 10. 三个反直觉的发现

### 10.1 过拟合 ≠ 变丑，而是「画面被压平」

1000 步的图，指标上非常难看：亮度从 166 拉到 213、std 从 60.9 掉到 22.6。
看起来像「练废了」。

但**用眼睛看**，它其实是另一种东西：极简、高亮、发光感的水彩，反而挺好看。

真正的问题在别处：**1000 步会把画面整体提亮约 35 个亮度单位**。
这在暗场景是救命（低步数的图脸整个没入黑暗，五官糊掉），
在亮场景就是灾难（白裙子直接顶爆，人像纸片人）。

### 10.2 低步数不是「安全牌」

直觉上会觉得「少训一点比较保险」。实测正好相反：

| 场景 | 100 步 | 1000 步 |
|---|---|---|
| 赛博暗室 | **脸完全黑了，五官消失** | 结构完整，脸是对的 |
| 海边奔跑 | **脸和肢体崩成一团白** | 过曝，但结构在 |

低步数的问题是**欠拟合**：它没学到足够的「人物结构先验」，
一遇到训练集里没出现过的光照或动作，就直接塌掉。

### 10.3 亮场景要**降**强度，暗场景不能降

因为「提亮」这件事本身就是强度驱动的：

- 亮场景：`0.6–0.8`，把过曝压住，肤色才留得住；
- 暗场景：**必须 `1.0`**，降下来脸就黑回去了。

还有一个细节：亮场景 `0.8` 虽然「不爆亮」，但**肤色会发白像纸片人**。
`0.6` 的肤色红润通透、裙褶和腿部光影都在。

> **「不爆亮」不等于「好看」。** 这条我们绕了两轮才想明白。

## 11. 方法论层面的一句话

> **参数是死的，眼睛是活的。**

这轮实验里最贵的两个教训都来自「指标说得通，但图不好看」：

1. 用亮度/std 判定 1000 步「过拟合练废」 → 被眼睛推翻；
2. 用「有没有爆亮」判定 0.8 比 0.6 好 → 被「肤色像纸片」推翻。

正确的用法是：**指标用来筛异常（黑场、纯色、明显崩坏），判断交给眼睛。**
指标永远不该成为结论，它只是把你从 180 张里筛到 18 张的工具。
